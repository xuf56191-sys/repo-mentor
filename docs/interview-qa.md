## 2026-08-19：V0.6 工作流核心概念（第一次复盘）

> 对应 Codex 完成的 8/17（条件路由）、8/18（证据循环）任务。
> 概念直觉已经建立，本卡片负责把术语和细节固化。

### Q1：用一句话介绍你的项目（电梯陈述）

**我的回答（原版）：**

> 一个面向新人的仓库学习 Agent。输入：学习者画像 + 目标任务 + 仓库路径；
> 输出：有真实源码证据支持的学习路线。核心是不编造：所有推荐都必须来自
> 真实仓库文件，路径存在 ≠ 内容已确认。

**改进版（面试用）：**

> RepoMentor 是一个面向开源新人的自适应仓库学习 Agent。它解决的核心问题是：
> 新手面对陌生仓库，不知道为了完成一个具体目标，下一步该读什么、学什么——
> 普通仓库分析报告很难变成可执行的学习计划。输入是学习者画像、目标任务和
> 仓库路径，输出是一份**有真实源码证据支持**的学习路线。
>
> 技术上，我用 LangGraph 搭了一套自适应工作流：共享状态管理、四个单一职责的
> 节点，加上条件路由——证据不足时会自动请求澄清或补读，而不是硬编。整套系统
> 有 197 个自动化测试，并且在三个真实仓库和一个实际贡献案例上做过验证。
>
> 最值得说的一点：我把『证据可信度』当成第一原则——所有推荐必须能追溯到真实
> 源码，路径存在不等于内容已确认，模型宁可承认不知道，也不编造。

**要点**：结尾留两个钩子（「自适应工作流」「197 个测试」）等着被追问。

### Q2：什么是条件路由？和普通 add_edge 有什么区别？

**我的回答（原版）：**

> 条件路由是两个节点之间的判断语句，满足这个条件就执行某个节点，
> 不能满足就执行另一个节点；add_edge 会直接进入下一个节点。

**参考答案（面试用）：**

> 条件路由 = `add_conditional_edges(源节点, 路由函数, path_map)`。
> - **路由函数**：只读 State，返回一个字符串 key（如 `"enough_evidence"`），
>   不调用 LLM、不改状态——只做"控制决策"；
> - **path_map**：key → 目标节点 的映射；
> - 普通 `add_edge` 是**固定路径**（编译时定死），条件边是**运行期动态决定**。
>
> 关键区分：**节点负责"改状态"，路由函数负责"选下一步"**——职责分开，
> 路由才能保持轻量、可测试、不花钱。

### Q3：证据补充循环（8/18）解决什么问题？route_after_evidence 的三条分支？

**背景**：工作流在仓库证据不足时，最多补读两个候选文件，
并在证据充分或达到限制时可预测地结束，不出现无限循环或无目的仓库读取。

**三条分支（口诀：够 → 生成；不够 → 补读；到顶 → 保守停）**：

| 分支 key | 去哪个节点 | 含义 |
|---|---|---|
| `enough_evidence` | `generate_roadmap` | 证据够了，正常生成路线 |
| `read_more` | `read_more_evidence` | 证据不够，补读一个候选文件，回到路由再判断（循环）|
| `stop` | `conservative_evidence_stop` | 预算/次数到顶，保守停止，明确缺什么、可补什么 |

**为什么叫「循环」**：`read_more_evidence` 读完 → 回到路由 → 可能再 `read_more`……
所以用三层保险保证终止：`max_steps=2`、`EvidenceBudget(max_files=2)`、`recursion_limit=20`。

**面试话术**：『我用条件边实现了一个带终止保证的证据补充循环。』

### Q4：State 里的可变对象为什么不能原地修改？（dataclasses.replace 的坑）

**背景**：8/18 用 `dataclasses.replace()` 复制 `EvidenceBudget`。

**问题**：
1. LangGraph 的 State 是所有节点**共享**的 dict；
2. 如果 State 里存了一个 `EvidenceBudget`（**可变对象**），多个节点拿到的是**同一个对象引用**；
3. 一个节点**原地修改**它（`budget.consume(...)` 改了 `used_files`），修改会**泄漏**到
   之前/之后的所有 State 快照——导致状态不可复现（Checkpoint 恢复时预算已被偷偷消费）；
4. 解法：**不原地改，创建副本**——`dataclasses.replace(budget, used_files=..., used_chars=...)`，
   把新对象返回给 LangGraph 覆盖旧引用。

**类比**：`replace` = 复印一份再改，而不是在原件上涂改。

**面试话术**：『我在 LangGraph 里处理过一个共享可变状态的坑——State 里不能放会被原地
修改的可变对象，我用 `dataclasses.replace` 创建副本，保证状态快照干净、可复现。』

### 复盘验证（2026-08-19 完成）

**Q2 验证**：条件路由由三个部分组成——**源节点、路由函数、path_map**；
路由函数**不能调用 LLM**（只读 State、返回 key）。✅ 已掌握

**Q3 验证**：三分支——`enough_evidence` → `generate_roadmap`（证据够，正常生成）；
`read_more` → `read_more_evidence`（不够，补读一个再回路由）；
到顶 → 停止循环（保守停止，说明缺什么）。✅ 已掌握

**Q4 验证**：最初答不上来，换讲法后理解。核心：
- 共享可变对象 = 大家共用同一张草稿纸，一人涂改全部可见；
- `replace` = 复印新纸再改，原件不动（不可变更新 immutable update）；
- 与 checkpoint 的关系：快照若引用被污染的纸，恢复历史就出错；
- 面试话术：『State 里不能放会被原地修改的可变对象，
  我用 dataclasses.replace 做不可变更新，保证快照干净可复现。』

## V0.8 文档加载与混合检索（2026-08-29/30）

### Q5：Loader 和 Retriever 的职责有什么区别？

**回答**：Loader 是准入和数据建模层，决定哪些文件可以安全读取，
并产生带仓库、学习模块、路径和行号的片段。
Retriever 只对已准入片段排名，不能为了回答问题绕过 Loader 自行扫描全仓。

### Q6：为什么 DocumentChunk 必须保留路径和行号？

**回答**：检索内容在 RepoMentor 中是学习证据，不是不可复核的自由文本。
路径和行号让用户能回到真实仓库核对，也让测试可以按行号还原原文。
实现中还要防止 Pydantic 清理开头空行造成行号偏移。

### Q7：代码文件为什么不只用固定字符长度切块？

**回答**：固定长度容易把函数签名、函数体和文档字符串分到不同块，
破坏语义完整性。当前使用 AST 的顶层类/函数起始行作为主边界，
只对过长语义单元再使用连续行窗口。

### Q8：为什么使用混合检索，而不是只用向量？

**回答**：自然语言问题可能使用与源码不同的表达，向量分数更适合这类改写。
但 `build_adaptive_graph`、`EvidenceBudget` 和文件路径是精确符号，
关键词匹配更准确。混合排名保留两类信号，并返回分项得分便于解释。

### Q9：当前的向量检索是神经 Embedding 吗？

**回答**：不是。当前是中英文/标识符特征、受控领域概念扩展和特征哈希向量的离线基线。
优点是不上传私有仓库、无 API 成本且完全可复现；
缺点是语义能力有限并可能有哈希碰撞。后续可替换向量编码器，
但准入、范围隔离和来源校验不应因此改变。

### Q10：为什么要有“证据不足”，不直接返回 Top-3？

**回答**：任何排名器都能给出第一名，但第一名不代表真正相关。
初次评测中，蛋糕问题因哈希碰撞得到小量向量分。
当前使用组合分门槛，且纯向量命中需要更高分数，
否则返回证据不足并请求更具体的文件或符号。

### Q11：如何评估 Retriever？

**回答**：除了单元测试，我用 RepoMentor 自身真实文件建立 10 个学习问题，
验证预期真实来源是否进入 Top-3，并用一个明确无关问题测试拒绝能力。
第一轮评测是 9/10 且存在无关问题误报，调整通用 symbol 权重和充分性门槛后达到 10/10。

## V1.0 贡献准备与界面（2026-08-31—09-09）

### Q12：如何保证学习问答不是模型幻觉？

**回答**：先由范围受限 Retriever 返回证据并判断充分性，只有充分时才组织答案；
答案引用真实路径、起止行和原文 excerpt。无证据时固定拒答，不能用模型常识补仓库事实。

### Q13：路线、测验和问答为什么必须复用同一证据层？

**回答**：如果各自重新加载和检索，范围、版本和证据可能不一致，也会重复 IO。
当前一次生成 `DocumentChunk`，三个消费者只在已有片段上查询，
并使用相同 repository/module scope ID。

### Q14：RAG/Retriever 应该怎样评测？

**回答**：正例检查期望真实来源是否进入 Top-K，负例检查越界问题是否拒答；
两类分别统计命中率和拒答率。不能只测“总能返回 Top-3”，因为排名第一不等于相关。

### Q15：为什么贡献准备度不能直接让 LLM 给百分比？

**回答**：自由百分比不可复算、难调试，也容易让用户误解为成功概率。
我使用五项固定评分卡，总分必须等于分项和；分数只代表能力与证据覆盖度，
不代表维护者会接受 PR。

### Q16：TargetIssue 为什么和 TargetTask 分开？

**回答**：TargetTask 是通用学习/开发目标，TargetIssue 还包含 labels、deadline、
Issue 描述和验收结果等贡献语义。分开后领域规则更明确，再转换成 TargetTask 复用路线能力。

### Q17：Streamlit 的 session_state、checkpoint 和 SQLite 有什么区别？

**回答**：session_state 服务当前页面交互；checkpoint 定位 LangGraph 节点的暂停/恢复；
SQLite 保存跨进程的路线、测验和掌握度。它们的生命周期和职责不同，不能互相替代。

### Q18：为什么 UI 业务逻辑放在 ui_service.py？

**回答**：控件层只收集输入和展示输出，模型校验、证据加载、评分和保存放在纯 Python 服务，
这样无需启动浏览器就能离线测试，也便于以后替换 Web 框架。

### Q19：这个项目和 RepoMind 类工具有什么不同？

**回答**：RepoMentor 不追求通用全仓问答，而是围绕特定学习者和特定 Issue，
输出每日学习任务、证据约束测验、掌握度和贡献准备度。
比较的是产品目标和范围，不对未实测的其他工具能力作贬低性结论。
