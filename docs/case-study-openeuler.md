# openEuler/openGauss 真实贡献案例验证

## 案例范围

- 验证日期：2026-09-02
- 本地仓库：`Plugin-source`（远端为 openGauss Plugin 仓的个人分支）
- 目标 Issue：Plugin #1626
- 任务：修复 Dolphin MySQL 协议下主键索引名称、重复键错误码和 SQLSTATE 与 MySQL 不兼容的问题
- 输入方式：本地仓库 + 人工粘贴 Issue/PR 草稿；没有自动访问社区或修改代码

这个案例来自实际本地仓库和已有的 PR 自验草稿。它属于 openEuler
生态上的 openGauss 实习贡献场景，但不能代表整个 openEuler 内核仓库。

## 人工入门路线（事实基线）

已有人工排查记录形成了下面的真实路径：

1. 用 Peewee、PyMySQL、MySQL 客户端和 gsql 做四层对照复现；
2. 将重复键异常定位到 `contrib/dolphin/plugin_protocol/handler.cpp`；
3. 将主键名称差异定位到 `public.index_statistic` 视图；
4. 同时检查安装、5.2→5.3 升级和 5.3→5.2 回滚 SQL；
5. 增加 JDBC 错误映射测试，并更新 `SHOW INDEX` 回归输出；
6. 根据仓库规范检查 `DOLPHIN` 宏、fastcheck、资料影响和回合分支。

人工过程已经完成复现、根因定位、代码修改、静态检查和测试补充；
完整 C++ 构建、Dolphin fastcheck、插件升级/回滚仍受环境限制，保持 WIP。

## RepoMentor 路线

RepoMentor 将该任务转换为 `TargetIssue`，再执行贡献差距分析和
`openEuler_mode`：

1. 结构化保存标题、详细描述、labels、预期结果和参考 Issue；
2. 从目标文本推导 Git 贡献流程、仓库代码定位、调试、自动化测试等能力；
3. 用固定五项公式计算准备度，而不是让模型随意给百分比；
4. 读取本地 README/CONTRIBUTING/项目元数据并生成环境、规范、前置知识清单；
5. 对未找到的贡献资料和未验证能力明确标记 `needs_confirmation`；
6. 不自动修复 Issue，也不把“生成建议”说成“已通过完整构建和 CI”。

## 有效推荐（至少 3 项）

1. **先限定具体 Issue。** 该案例跨错误包、元数据视图、升级脚本和测试，
   如果只有“学习 Dolphin”这一宽泛目标，路线无法验收；`TargetIssue` 的
   描述和 expected outcome 校验能阻止这种模糊输入进入后续流程。
2. **贡献规范优先于直接改代码。** 本地 README 明确要求 `.h/.cpp` 使用
   `DOLPHIN` 宏，并要求考虑 check 用例和升级/回滚。这与真实 PR 自验项一致。
3. **测试能力必须单独计分。** 真实案例需要 JDBC 回归、`SHOW INDEX`
   预期输出、fastcheck 和升级/回滚验证；准备度公式不会因为会写 C++ 就默认测试已准备好。
4. **能表达证据不足。** 完整构建环境和跨仓 `AUTO_INCREMENT` 问题均未验证，
   系统应保留限制，而不是生成“问题已经解决”的结论。

## 无效推荐与局限（至少 3 项）

1. **当前 V0.8 索引类型过窄。** 定向加载器主要支持 Markdown、Python、
   测试和配置文件，尚不能直接索引本案例最关键的 C++、SQL 和 Java 文件；
   因而文件推荐不能替代人工已经完成的源码定位。
2. **没有远程社区上下文。** 系统不会自动读取 Issue #1626、SIG 会议结论、
   维护者意见和 CI 状态，这些仍需用户手动提供或人工确认。
3. **不能验证重型环境。** RepoMentor 无法证明 openGauss-server 全量编译、
   Dolphin fastcheck 或插件升级/回滚成功；这些是外部环境验收，不是文本分析。
4. **准备度不是合入概率。** 分数只表示已定义能力和证据覆盖度，不能预测维护者是否接受 PR。

## 耗时对比

历史人工过程没有从开始到完成的统一计时记录，因此本案例**不能诚实计算**
“节省了多少小时”。RepoMentor 的本地结构化和清单生成是秒级操作，但它只覆盖
目标整理和准备检查，不能与包含环境搭建、复现、编码和测试的人工全过程直接比较。

后续验证必须同时记录：人工定位开始/结束时间、RepoMentor 运行时间、人工复核时间，
并把“机器生成清单”和“完成贡献”分开计时。当前结论只评价推荐质量，不宣称效率提升。

## 验证结论

RepoMentor 对“明确目标、阅读规范、暴露能力缺口、保守表达限制”有效；
对该实际 C++/SQL/Java 跨文件 Issue 的源码定位仍不足。最合理的下一步是扩展安全文件类型，
再用人工已确认的目标文件作为期望来源建立评测，而不是直接扩大到全仓扫描。
