# RepoMentor Design Decisions

## ADR-001：使用单一状态图，而不是自由式多 Agent

- 状态：Accepted
- 日期：2026-08-20
- 适用版本：V0.6

### 背景

RepoMentor V0.6 需要依次完成：

1. 检查用户输入；
2. 分析学习者；
3. 分析目标任务；
4. 收集仓库证据；
5. 在证据不足时有限补读；
6. 生成学习路线；
7. 等待人工确认；
8. 修改目标后重新规划。

这些步骤共享 `AgentState`，并且具有明确的执行顺序、
停止条件和人工确认边界。

### 决策

V0.6 使用一个 `StateGraph` 组织确定性节点、条件边、
有限循环和 checkpoint，不引入由多个自主 Agent
自由协商、转交任务的架构。

### 为什么选择单一状态图

#### 1. 控制流明确

RepoMentor 当前处理的是一条依赖关系明确的学习规划流水线。
例如，只有完成输入检查后才能建立严格领域模型；
只有获得学习者分析和目标分析后才能判断哪些仓库证据相关；
只有获得内容证据后才能生成可信的学习路线。

这些关系适合通过固定 Edge 显式表达执行顺序，
并通过 Conditional Edge 表达输入不足、证据补读、保守停止和人工修订。
每一个路由键都有确定目标，因此开发者可以直接从图中判断
某个 State 会进入哪条路径，不需要依赖多个 Agent 临时协商下一步。

#### 2. 状态容易追踪

所有节点通过同一个 `AgentState` 交换数据，
学习者画像、目标分析、仓库证据、补读次数、错误信息、
学习路线和人工确认状态都有明确字段。

节点只返回自己负责的局部更新，LangGraph 再根据字段的 reducer
执行覆盖或累积。这样可以检查任意 checkpoint，确定某个结果由哪个节点产生，
也可以在目标修改后明确清空已经失效的分析、证据和路线。
如果多个自主 Agent 分别维护私有上下文，
同一份证据和路线可能存在多个版本，状态同步和问题定位会更困难。

#### 3. 更容易测试

节点函数、路由函数和整张图可以分层测试。
节点测试验证输入 State 会产生哪些局部更新；
路由测试验证特定状态会返回哪个路由键；
图级测试验证节点连线、有限循环、checkpoint 恢复和会话隔离。

除 `generate_roadmap` 外，当前主要控制逻辑都由确定性 Python 规则实现。
测试中可以使用 monkeypatch 替换真实 LLM，
使测试不联网、不产生模型费用，并能够稳定复现。
自由式多 Agent 的协商过程通常包含多次模型决策，
同一输入可能产生不同的交接顺序和结果，测试成本更高。

#### 4. 成本和延迟更可控

当前只有 `generate_roadmap` 节点需要调用 LLM，
输入检查、条件路由、文件读取限制和人工确认路由都使用本地规则。
因此一次工作流的主要模型成本是可估算的。

如果把学习者分析、目标分析、证据收集和路线生成都设计成自主 Agent，
每个 Agent 可能需要单独调用模型来制定计划、解释结果和决定交接对象，
Agent 之间还需要重复传递或总结上下文。
这会增加 token 消耗、网络往返次数和整体延迟，
但当前顺序型任务无法从这些额外调用中获得足够收益。

#### 5. 安全边界更清楚

仓库读取必须经过现有安全工具和预算限制。
`read_more_evidence` 每次只读取一个未尝试候选文件，
`max_steps=2` 和 `EvidenceBudget` 限制补读次数、文件数和字符数；
敏感路径和被忽略路径仍由仓库读取工具拒绝。

路线生成后，`confirm_roadmap` 使用 `interrupt()` 暂停工作流，
只有经过 `RoadmapConfirmation` 严格校验的 `approve` 或 `revise`
才能继续。将这些边界写成显式节点、状态字段和条件边，
可以通过测试证明工作流不会无限读取仓库、绕过人工确认或混用旧路线。
自由式 Agent 如果可以自行决定继续读取或跳转，
则需要额外权限系统才能达到相同的可控性。

### 没有选择自由式多 Agent 的原因

自由式多 Agent 更适合存在多个真正独立的角色，
并且这些角色需要分别规划、并行工作或协商结果的场景。
